# APIOps CLI Part 2: Toolkit Migration Demo

This section demonstrates how to migrate an existing APIOps Toolkit repository
to APIOps CLI without rebuilding its APIM artifacts.

## Demo goal

Show that an existing Toolkit implementation can be modernized by:

1. Preserving the current implementation for comparison.
2. Generating the new APIOps CLI repository files.
3. Using Copilot to compare the old and new configuration formats.
4. Translating the existing filters, overrides, tokens, and workflows.
5. Validating the existing Toolkit artifacts with the new CLI.

Repository:

```text
anotherRedbeard/apiops-demo
```

Legacy starting point:

```text
demo-part2-start
```

## Start from the Toolkit implementation

```bash
cd /Users/andrewredman/src/apiops/apiops-demo
git switch -c demo/migration-live-YYYYMMDD demo-part2-start
git status
```

Show the existing implementation:

```bash
ls -1 configuration*.yaml
find .github/workflows -maxdepth 1 -type f | sort
find apimartifacts -type f | wc -l
cat package.json
```

Talking points:

- `apimartifacts/` already contains the API Management configuration.
- The repository uses the older Toolkit workflows and configuration schemas.
- Environment overrides and secret replacement are already established.
- The migration should preserve these investments rather than start over.

## Preserve the Toolkit files

Rename the existing configuration files so they can be compared side by side
with the files generated by APIOps CLI:

```bash
mv configuration.extractor.yaml configuration.extractor.toolkit.yaml
mv configuration.dev.yaml configuration.dev.toolkit.yaml
mv configuration.prod.yaml configuration.prod.toolkit.yaml

cp package.json package.toolkit.json
cp package-lock.json package-lock.toolkit.json
```

Explain that running `apiops init --force` directly would overwrite meaningful
files. Preserving the originals makes the migration reviewable and reversible.

## Generate the APIOps CLI files

```bash
npx -y @azure-tools/apiops-cli@latest init \
  --ci github-actions \
  --artifact-dir ./apimartifacts \
  --environments dev,prod \
  --non-interactive
```

The existing `apimartifacts/` directory remains in place. The CLI generates:

```text
.github/workflows/run-apiops-extractor.yml
.github/workflows/run-apiops-publisher.yml
.github/prompts/
APIOPS-WORKFLOW-IDENTITY-SETUP.md
configuration.extractor.yaml
configuration.dev.yaml
configuration.prod.yaml
package.json
```

## Use Copilot to compare and translate

Open the Toolkit and CLI files side by side:

```bash
code \
  configuration.extractor.toolkit.yaml \
  configuration.extractor.yaml \
  configuration.dev.toolkit.yaml \
  configuration.dev.yaml \
  configuration.prod.toolkit.yaml \
  configuration.prod.yaml
```

Ask Copilot to:

```text
Compare each APIOps Toolkit configuration file with the generated APIOps CLI
file. Preserve the intent and environment-specific behavior, but translate the
configuration to the current CLI schema and token syntax. Explain each required
change before applying it.
```

The important changes Copilot should identify are:

| Toolkit | APIOps CLI |
|---|---|
| `subscriptionNames` | `subscriptions` |
| `apimServiceName` in override files | Removed; service is supplied through `--service-name` |
| `{#tokenName#}` | `{#[TOKEN_NAME]#}` |
| API entry containing only diagnostics | Add `properties: {}` |
| Separate Toolkit executable workflows | Unified `npx apiops extract` and `npx apiops publish` |

Use the existing GitHub environment variables rather than creating duplicates:

```text
RESOURCE_GROUP_NAME
APIM_INSTANCE_NAME
AZURE_SUBSCRIPTION_ID
```

## Preserve the existing package

The generated `package.json` must not replace the developer-portal
dependencies.

Ask Copilot to merge the generated APIOps CLI dependency into the original
package while retaining:

```text
@azure/storage-blob
mime
yargs
```

The resulting package also contains:

```json
"@azure-tools/apiops-cli": "latest"
```

Add:

```text
node_modules/
```

to `.gitignore`.

## Review the generated workflows

Compare the new workflows with the Toolkit workflows.

Talking points:

- The extractor and publisher now invoke the same `apiops` package.
- GitHub OIDC replaces stored Azure client-secret authentication.
- Existing `dev` and `prod` GitHub environments are reused.
- Environment variables select the resource group and APIM service.
- Key Vault values remain runtime values and are not committed.
- The publisher performs a dry-run before a real deployment.

Correct the generated artifact path trigger:

```yaml
paths:
  - 'apimartifacts/**'
  - 'configuration.*.yaml'
```

The generated leading `./` did not match artifact-only pull-request changes
during rehearsal.

## Validate backward compatibility

The important migration proof is that the existing Toolkit artifacts do not
need to be converted.

The full artifact set was validated with APIOps CLI 1.0.4:

```text
135 creates/updates
0 patches
0 deletes
```

Talking point:

> We changed the tooling and configuration schema, but the existing APIM
> artifacts remained usable by the new CLI.

Two product subscriptions with hexadecimal resource IDs were skipped because
the CLI classified them as APIM-generated. The existing workflow handles the
one explicitly managed subscription key separately with values retrieved from
Key Vault. This does not affect the broader artifact compatibility
demonstration.

## Switch from Toolkit to CLI workflows

Once the CLI workflows are ready, disable the old Toolkit workflows so both
publishers cannot run for the same change:

```bash
gh workflow disable run-extractor.yaml
gh workflow disable run-publisher.yaml
gh workflow disable run-publisher-with-env.yaml
```

Leave the developer-portal workflows active.

Verify:

```bash
gh workflow list --all
```

Expected result:

```text
disabled_manually  Run - Extractor
disabled_manually  Run - Publisher
disabled_manually  Run Publisher with Environment
active             Run APIM Extractor
active             Run APIM Publisher
```

## Migration summary

Close the demo with:

1. We preserved the existing Toolkit files.
2. APIOps CLI generated the new repository structure.
3. Copilot compared the old and new schemas and translated the configuration.
4. Existing artifacts were validated without conversion.
5. Existing GitHub environments, OIDC identities, and Key Vault integration
   were reused.
6. The old Toolkit workflows were disabled after the CLI workflows were ready.

The migration is primarily a tooling and pipeline modernization, not a redesign
of the APIOps operating model.
